一、Agent开发的起点：把一切塞进Prompt

假设我们要实现一个功能，用户输入股票的部分名称或股票代码，例如：

“腾讯”、“腾讯控股”、“Tencent”、“0700”

系统需要完成几件事：

*判断输入是股票名称还是股票代码

*匹配最可能的股票

*返回结构化基础信息，包括股票代码、英文名、中文名、上市地区、交易货币

如果你刚接触Agent开发，写出来的代码大概率会是这样：

``import { initChatModel } from"langchain";import { SystemMessage, HumanMessage } from"@langchain/core/messages";import"dotenv/config";asyncfunction main() {    const model = await initChatModel("gemini-2.5-flash", {        modelProvider: "google-genai",        temperature: 0,    });    const SYSTEM_PROMPT = `你是一个股票识别助手。用户会输入一个模糊的股票查询（可能是中文名、英文名、简称、代码等），你需要从美股、港股、A股中找到最可能匹配的股票。    返回一个 JSON 数组，每个元素包含：    - ticker: 股票代码（美股如 "AAPL"，港股如 "0700.HK"，A股上交所如 "600519.SS"，深交所如 "000858.SZ"）    - name: 英文全称    - nameCN: 中文名称    - region: 地区（如 "US", "HK", "CN"）    - type: 类型（如 "CS" 表示普通股, "ETF" 表示指数基金）    - currencyName: 交易货币（如 "USD", "HKD", "CNY"）    规则：    1. 最多返回 5 个最相关的结果    2. 优先返回最知名、市值最大的匹配    3. 如果查询明确指向某只股票，只返回该股票    4. 如果同一公司在多个市场上市（如阿里巴巴 BABA + 9988.HK），都列出    5. 只返回 JSON 数组，不要任何解释文字`;    const prompt = [        new SystemMessage(SYSTEM_PROMPT),        new HumanMessage('帮我找一下腾讯公司股票'),    ];    const result = await model.invoke(prompt);    console.log(result.content);}main();``

所有逻辑都写进一个巨大的Prompt。Prompt里既包含：

*判断是代码还是名称的逻辑

*决定如何查询的规则

*结构化输出格式的定义

模型像一个“万能函数”，把所有规则丢进去，它帮你完成一切。

从某种角度看，这确实是Agent开发的本质：

把输入组织成Prompt，交给LLM推理，再解析结构化结果。

但问题也很明显。当所有逻辑都耦合在一个Prompt里时，这个Prompt就变成了一个“巨型组件”。它既负责路由判断，又负责数据查询，还负责格式转换。就好像写了一个1000行的大文件，维护的时候眉头一皱，扑面而来的屎山味。

既然React可以通过组件拆分来降低耦合，那 Agent 开发能不能也用模块化的思路来重构？把判断逻辑拆成一个Router，把查询逻辑拆成一个Tool，把结构化输出拆成一个Parser。

当然可以。

二、Agent的模块化：像拆React组件一样拆Prompt

可以将Agent拆解为四个最常见的模块：PromptTemplate / Router / Tool / Parser。

PromptTemplate：将Prompt从拼接字符串变成了“可变模版”

类似于前端组件的props，只需要传入不同的参数，就能得到不同的prompt。同一个模板可以喂不同的输入，方便复用和调试。

Router：把“路由层”从 Prompt 里拆出来

很多巨型Prompt的第一段都在判断用户到底想要干什么，需要把它抽离为意图路由。顾名思义，类比于前端的路由层，应该单独抽离出来，让这一部分职责单一。

Tool：把“API”从 Prompt 里拆出来

需要事实正确的，就不要只用 prompt。大模型有幻觉，查股票等涉及到具体数据的，都不应该靠模型在文本中猜。Tool类比前端的API请求/Service层。最好能直接用tool来获得数据，让model单纯来消费数据。

Parser：把“结构化输出”从 Prompt 里拆出来

巨型Prompt的最后一段往往都在规定输出格式。这件事放在Prompt中，会出现输出不稳定的情况（字段丢失、类型错误等）。Parser的意义是，把结构化的输出变成一个独立的模块，确保返回的结构是有保证的。类比于前端typescript的返回类型声明。

代码已经清晰了很多。先关注最后几行的Step，我们可以清晰的看到分成了路由、工具调用、格式化输出三层。

但是又有问题了：假设现在想添加一个自动记录耗时的能力，我需要在3个Step前后都添加时间打点，平白让代码中添加了很多样板代码，导致我的代码又不好复用了。

而且LLM返回很慢，我想让这条chain做流式输出，就得进入Step3改动其内部的逻辑，因为目前它是await的但做不了。如果改造完成后还有个链也用到了Step3，但是希望直接完整返回呢？

随着链路变复杂，纯手写 await 会逐渐暴露出一堆“编排层”的工程痛点：

*统一观测很难：想要每一步自动打点、记录耗时、token usage、错误栈、trace id……最后会变成每个函数里塞一堆重复样板代码。

*重试/超时/取消很难做成一致语义：路由失败重试几次？tool 超时怎么 fallback？用户断开连接怎么把整条链取消？靠手写逻辑很快就会散落在各处。

*并行与分支会把代码写爆：比如同时按“名称”和“代码”两路搜，取更置信的结果；或者先并行召回多个检索器再汇总——Promise.all 能写，但一旦再叠加 tracing、限流、缓存、stream 透传，复杂度会指数级上升。

*复用与组合变差：当你想把“Router + Tools + Parser”这套能力抽出来给别的业务复用，你会发现你复用的是一堆函数 + 一堆约定，而不是一个“可插拔、可配置、可观测的执行单元”。

要解决这些问题，LangChain给出的答案就是Runnable。

三、Runnable：可组合的通用执行单元

第二部分遇到的问题，在前端领域也曾经存在过。还记得我们刚学习React的时候，开篇明义说的是什么吗？

React是一个MVVM模型。

在React之前，前端都是直接通过MVC来操作DOM的，会有状态混乱、更新顺序难以控制，错误边界缺失等一系列的问题。

React是怎么解决这个问题的？React 定义了组件的概念，给组件定义了一系列的生命周期和方法。之后，组件之间的组合，我们就不需要思考：

*组件什么时候被挂载、什么时候被销毁

*手动管理父子组件之间的更新顺序

*自己实现状态变更后的脏检查与重渲染

*手写 DOM diff 与节点复用逻辑

*关心事件如何在组件树中冒泡与绑定

*为每个组件单独实现日志、错误边界与调试钩子

我们只需要关注：组件接收什么props，产出什么UI。底层的生命周期调度、更新队列、批处理策略、异常捕获、渲染优化，都由React框架统一管理。

把这个类比放回Agent开发上：如果没有统一的执行单元，我们就像在手写 DOM 操作一样，用await一段段把控制流拼起来。

代码当然能跑，但一旦希望“增加点通用能力”，问题就来了：流式、透传、取消、重试、超时、并行调度、缓存、Tracing——这些切面能力会被迫散落在每个await节点周围，最后变成一堆难以复用的样板代码。

因此在模块化之后，LangChain还需要引入Runnable，为了让框架能在不侵入你业务代码的情况下，提供流式、并发、异步等多种运行形态，并提供并行、分支、重试、超时、缓存、回调/Tracing 等“默认能力”。

Runnable：LangChain中可组合的通用执行单元

在React中，UI和交互被抽象为函数式组件。然后，小组件组合成大组件，大组件组合成页面，页面组合成系统UI。

在LangChain中，可执行模块被被抽象为Runnable。然后，不同Runnable组合成一条执行链（子Agent），不同的子Agent又组合成Multi Agent（LangGraph的部分）。

LangChain中把自己的核心区块都设计为了Runnable：ChatOpenAI 是 Runnable，OutputParser 是 Runnable，自定义逻辑也是 Runnable。

这样大家的默认能力就统一了，可以在不侵入业务代码的情况下，完成不同的逻辑工作。所以，我们现在简单改造一下上面的代码，就可以在不影响每个节点的情况下，让链做流式输出；也可以轻松的就给节点记录耗时、让节点重试等。

回过头来看我们的代码，

`const chain = routeStep    .pipe(toolStep)    .pipe(buildPromptStep)    .pipe(model);`

但是可以看到各个Runnable是通过pipe串联到一起的。而在实际的应用中，Agent开发编排的控制链是一个复杂的系统，必然涉及到条件分支、并行串行、循环嵌套这些操作。那怎么办呢？

这个时候就得引出LCEL（LangChain Expression Language）——LangChain的声明式表达。

四、LECL：Runnable的数据流图

LCEL可以类比为前端的JSX。

想象一下，在前端中，我们定义了很多Component，这些组件是如何拼接起来的呢？

`function Page() {   // 一些逻辑   const [loading, setloaing] = useState(false);   return (       <A>           <B />           <C />           {loading && <D />}       </A>   )}`

JSX是前端组件树的声明式表达。声明式表达是一个Schema，它核心关注的是结构定义，描述了数据如何流动、哪些步骤并行、哪些步骤串联、哪些步骤属于同一层。

当系统复杂度上升时，使用声明式表达有三个好处：

数据流链路足够清晰

例如，我们用代码逻辑包裹Runnable，就没有直接将逻辑抽象为一个Schema清晰。下面的Schama，一眼就知道链上各个节点的串并行依赖关系。

`// 命令式代码逻辑包裹Runnableif (input.flag) {  RunnableA;} else {  RunnableB;}const results = awaitPromise.all([  RunnableC,   RunnableD,   RunnableE,]);try {   RunnableF;} catch {   RunnableG;}// 声明式代码抽象为Schemaconst chain = RunnableSequence.from([// ① if / else  RunnableBranch.from([    [      RunnableLambda.from((input) => input.flag === true),      RunnableLambda.from(() =>"A")    ],    RunnableLambda.from(() =>"B")  ]),// ② Promise.all  RunnableParallel.from({    c: RunnableLambda.from(() =>"C"),    d: RunnableLambda.from(() =>"D"),    e: RunnableLambda.from(() =>"E")  }),// ③ try / catch  RunnableLambda.from((input) => {    if (!input.ok) {      thrownewError("fail")    }    return"F"  }).withFallbacks({    fallbacks: [      RunnableLambda.from(() =>"G")    ]  })])`

执行策略可以独立演进

在命令式代码中，结构和执行策略耦合在一起。如果需要将链改动为流式输出，就要改动其中的Runnable子节点。但是在声明式结构中，我们可以自动修改chain上或者某个节点的执行策略，举个例子：

`// 不使用LCEL的基础版const a = await stepA(input);const b = await stepB(a);const c = await stepC(b);return c;// 使用LCEL可以自由添加Chain的执行策略const chain = RunnableSequence.from([    // 给不同Runnable添加个性化的策略且不影响业务代码    stepA.withRetry(),    stepB.assign(),    stepC.withFallbacks()// 整体流式输出]).stream(input);`

可组合性大大提升

命令式写法复用的是函数，声明式写法复用的是“结构”。声明式代码天生就容易支持复杂的组合逻辑嵌套，例如嵌套、子图复用等，这为我们后续实现更加复杂的chain打下了基础。

其实也好理解，没有JSX的抽象，我们如何把一个个组件拼接在一起呢？那简直就是噩梦。

五、总结

React 解决的是 UI 执行调度问题；LangChain 解决的是 LLM 编排执行调度问题。但抽象层面，它们处理的是同一类问题：如何管理复杂系统的执行结构。

使用React来类比学习LangChain，可以取得事半功倍的效果。

尽管名字不同、实现不同，底层原则却高度一致：

*单一职责：让每个模块只做一件事

*模块化拆分：把复杂系统拆成可复用的单元

*声明式表达：描述结构，而不是堆砌控制流

*统一调度：由框架接管执行策略，而不是让业务代码承担调度复杂度

大道殊途同归，这才是架构的魅力啊。

AI时代，编程原理不是不重要了，而是更重要了。架构的品味之于程序员，就像是拳法之于拳师，决定了一个人能用AI提升效能的上限。

不懂原理，也能用 AI 抡出一堆“能跑”的代码，但真正的可扩展系统、可演进结构、可维护工程，永远建立在对抽象的理解之上。
